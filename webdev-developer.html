🔥 웹·앱 개발 기초 — 개발자편

대상: 바이브코딩으로 결과는 내지만 구조·데이터·운영 규율을 직접 설계하려는 학습자 · 목표: 3계층 아키텍처와 데이터 모델을 설계해 도구에 명세로 지시하고 AI 코드를 검증·보안 점검한다 · 약 4~5시간

목차

1. 앱 아키텍처 (3계층 분리) 2. 데이터 모델링 (ERD·PK/FK) 3. 인증·보안 기초 4. 성능 기초 5. SE 실천 6. 도구 vs 나 7. 실습: 정적→동적→API→배포 8. 더 배우려면 출처
최종 검토일 2026-06-26 · 웹 기술·보안 표준·도구 가격은 자주 바뀝니다. 수치·항목은 본문 하단의 공식 출처에서 최신본을 확인하세요.

핵심 메시지. 바이브코딩은 "타이핑"을 대신해 줄 뿐, "생각"을 대신해 주지는 않습니다. 개발자편의 목표는 코드를 손으로 짜는 능력이 아니라, 무엇을 만들지 설계하고(아키텍처·데이터 모델), 만들어진 것을 검증하는(테스트·보안) 능력입니다. AI는 앱이 돌아가게(run) 만드는 것을 최적화하지, 안전하게(safe) 작동하도록 최적화하지 않습니다.

심화: 버전관리·테스트·CI/CD·SOLID·Clean Code의 전체 그림은 소프트웨어 엔지니어링 가이드에서 더 깊게 다룹니다. 이 교안은 그 가이드로 가는 토대입니다.

1. 앱 아키텍처 — 프론트/백/DB 3계층 분리

현대 웹 앱의 표준 골격은 세 층의 분리입니다.

┌─────────────────────────────────────────────────────┐
│  프론트엔드 (클라이언트)                                │
│  HTML·CSS·JS / React 등 — "보여 주고 입력받는 층"        │
└───────────────────┬─────────────────────────────────┘
                    │  HTTP 요청/응답 (JSON, REST API)
┌───────────────────▼─────────────────────────────────┐
│  백엔드 (서버)                                          │
│  라우팅·비즈니스 로직·인증 — "판단하고 처리하는 층"        │
└───────────────────┬─────────────────────────────────┘
                    │  쿼리(SQL 등)
┌───────────────────▼─────────────────────────────────┐
│  데이터베이스                                            │
│  데이터의 영구 저장·조회 — "기억하는 층"                  │
└─────────────────────────────────────────────────────┘

이렇게 나누는 이유는 SE의 관심사 분리·모듈화(modularity)입니다. 각 층이 정해진 창구(API)로만 대화하므로, 디자인을 바꿔도 데이터 구조는 안 건드리고, DB를 교체해도 화면은 그대로 둘 수 있습니다. 또한 보안(중요 로직은 백엔드), 확장성(층별로 따로 키우기), 협업(층별 분업)이 쉬워집니다.

신뢰 경계. 서버는 클라이언트와 분리된 컴퓨터이므로, 클라이언트가 보낸 것을 절대 무조건 믿으면 안 됩니다. 브라우저(클라이언트) 코드는 사용자가 들여다보고 조작할 수 있습니다. 그래서 비밀번호 검증·결제·권한 확인 같은 "신뢰가 필요한 일"은 반드시 백엔드에서 합니다.

✓ 체크포인트 자기 앱에서 "이 처리는 화면(프론트)에서 해도 되는가, 서버(백)에서 해야 하는가?"를 3가지 기능에 대해 답할 수 있으면 OK.

2. 데이터 모델링 — ERD 사고와 PK/FK

코드를 짜기 전에 데이터 구조부터 그리는 것은 SE의 핵심 습관입니다. ERD(Entity-Relationship Diagram)는 "어떤 데이터(개체)가 있고, 그것들이 어떻게 연결(관계)되는가"를 그린 설계도입니다.

  • 개체(Entity): 저장할 "것". DB의 표 하나. (사용자, 게시물, 댓글)
  • 속성(Attribute): 개체가 가진 정보. 표의 열. (사용자 → 이름, 이메일, 가입일)
  • 관계(Relationship): 개체 간 연결. 카디널리티로 표현 — 1:1(한 사용자 ↔ 한 프로필), 1:N(한 사용자 ↔ 여러 게시물, 가장 흔함), N:M(여러 학생 ↔ 여러 강의).

블로그 앱의 간단한 ERD 예:

[사용자 User]              [게시물 Post]            [댓글 Comment]
 - id (PK)        1    N    - id (PK)        1   N   - id (PK)
 - email        ────────▶  - title        ───────▶  - body
 - name                    - body                    - post_id (FK)
 - created_at              - user_id (FK)            - user_id (FK)
                           - created_at
  • PK(Primary Key): 각 행을 유일하게 구분하는 열(보통 id).
  • FK(Foreign Key): 다른 표를 가리키는 연결고리. Post.user_id가 User.id를 가리키면 "이 글은 이 사용자가 썼다"가 표현됩니다.

데이터베이스 선택. 대부분의 바이브코딩 결과물은 관계형(SQL, 예: Supabase=PostgreSQL)을 씁니다. 표(table) 기반·복잡한 질의에 강합니다. 비관계형(NoSQL, 예: MongoDB·Firebase)은 문서·키-값 형태로 스키마가 자유롭고 빠른 시작에 유리합니다.

도구 지시 요령. "사용자 / 게시물 / 댓글 표를 만들고, 게시물은 사용자에 1:N으로 연결해 줘"처럼 ERD 언어로 지시하면 도구가 훨씬 정확한 DB를 만듭니다. ERD 사고는 "막연한 아이디어"를 "구현 가능한 명세"로 바꾸는 번역기입니다.

✓ 체크포인트 자기 앱의 핵심 개체 3개를 정하고, 그 사이 관계(1:N 등)와 각 표의 PK·FK를 종이에 그릴 수 있으면 OK.

3. 인증·보안 기초 — 비밀키 관리와 OWASP 맛보기

3.1 인증과 인가

  • 인증(Authentication): 신원 확인. "당신이 본인이 맞습니까?" (로그인)
  • 인가(Authorization): 권한 확인. "이 글을 삭제할 수 있습니까?" (권한)

웹은 본래 상태가 없는(stateless) 프로토콜이라, 로그인 상태를 유지하려면 매 요청에 신분증(쿠키/세션 또는 토큰, 예: JWT)을 함께 보냅니다. HTTP 401 Unauthorized(로그인 안 됨)와 403 Forbidden(로그인했지만 권한 없음)이 각각 인증·인가 실패에 대응합니다.

3.2 비밀키(secret) 관리 — 바이브코딩 1순위 보안 과제

AI 어시스턴트는 API 키·DB 비밀번호·토큰을 소스 파일에 직접 써 넣는 코드를 흔히 생성합니다. 2026년 가장 빈번한 사고 유형입니다.

  1. API 키를 코드에 절대 두지 않습니다. 환경 변수(.env)를 사용합니다.
  2. 첫 커밋 전에 .env를 .gitignore에 추가합니다.
  3. GitGuardian·TruffleHog 같은 도구로 커밋의 노출 비밀키를 자동 스캔합니다.
  4. GitHub의 비밀 스캐닝 + push protection을 켭니다.

실제 사고. 한 서비스가 AI가 허용적(permissive) 설정으로 스캐폴딩한 DB를 사람이 검토하지 않고 그대로 배포 → 인증 토큰 150만 건, 이메일 3.5만 건 노출. 교훈: "AI가 만든 인프라 설정을 사람이 읽지 않으면 그대로 출하된다."

3.3 OWASP Top 10:2025 맛보기 (바이브코딩 직결 3선)

항목바이브코딩 학습자가 기억할 점

입력 검증. 신뢰할 수 없는 입력(폼·URL 파라미터·외부 API)은 서버 측 검증을 기준선으로 삼고(클라이언트 검증은 UX 보조), 허용 목록(allow-list)이 차단 목록보다 안전합니다. 파라미터화 쿼리/ORM으로 SQL 인젝션을, 출력 인코딩으로 XSS를 막습니다.

✓ 체크포인트 자기 프로젝트에 .gitignore가 .env를 포함하는지 확인하고, "AI가 키를 코드에 박았는지" 한 번이라도 검색해 봤으면 OK.

4. 성능 기초

성능은 "사용자가 기다리지 않게" 만드는 일입니다. 개발자편에서 알아 둘 핵심 레버:

  • 렌더링 순서: 브라우저는 HTML을 위에서부터 읽으며 DOM을 만들고 CSS로 꾸미고 JS를 실행합니다. 무거운 스크립트를 <body> 끝에 두거나 defer로 미루면 첫 화면이 빨리 뜹니다.
  • 비동기·로딩 상태: 서버 왕복은 시간이 걸립니다. async/await로 화면이 얼지 않게 하고, 로딩 스피너로 진행을 알립니다.
  • 불필요한 요청 줄이기: 같은 데이터를 반복 요청하지 말고 캐시(브라우저 캐시·localStorage·메모리)를 활용합니다. 이미지는 적절한 크기·포맷(WebP 등)으로.
  • N+1 쿼리 피하기: DB에서 목록을 가져올 때 행마다 추가 쿼리를 날리면 느려집니다. 한 번에 조인(JOIN)하거나 일괄 조회합니다.
  • 측정 먼저: 추측으로 최적화하지 말고 브라우저 개발자도구(F12)의 Network·Performance 탭으로 병목을 먼저 찾습니다.

도구가 놓치기 쉬운 곳. AI는 "동작하는" 코드를 만들지만 N+1 쿼리·과도한 리렌더 같은 성능 함정을 자주 남깁니다. 느리다고 느끼면 측정부터 합니다.

✓ 체크포인트 자기 앱에서 Network 탭을 열어 "가장 오래 걸리는 요청 1개"와 "가장 큰 파일 1개"를 짚을 수 있으면 OK.

5. SE 실천 — 커밋 단위·테스트·CI/CD·SOLID/Clean Code

AI가 한 번에 많은 코드를 생성할수록, 출하하는 양과 검증할 수 있는 양의 간극이 벌어집니다. SE 실천은 이 간극을 통제하는 안전벨트입니다. DORA 2025 보고서의 한 줄: "AI는 팀을 고치지 않는다 — 이미 있는 것을 증폭한다."

5.1 Git 커밋 단위 — 작고, 의도가 분명하게

  1. 하나의 커밋 = 하나의 논리적 변경(atomic commit). "기능 추가 + 버그 수정 + 오타"를 한 커밋에 섞지 않습니다.
  2. 커밋 본문은 "무엇"이 아니라 "왜"를 적습니다. 무엇이 바뀌었는지는 diff가 보여 줍니다.
  3. 자주 커밋합니다. AI가 만든 변경이 "작동하는 지점"마다 커밋해 두면 다음 프롬프트가 망가뜨렸을 때 안전하게 복귀합니다.

Conventional Commits — 기계가 읽고 사람이 일관되게 쓰는 표준 포맷:

<type>(<scope>): <description>

<body — 왜 이 변경이 필요한가>

주요 type: feat(새 기능), fix(버그 수정), docs(문서), refactor(리팩터링), test(테스트), chore(빌드/도구).

5.2 테스트 — 단위·통합·Test-First

        /\        E2E (소수, 느림) — 실제 흐름 전체 검증
       /  \
      /----\
     / 통합  \     통합 테스트 (중간) — 모듈·DB·API 연동 검증
    /--------\
   / 단위 Test \   단위 테스트 (다수, 빠름) — 함수 하나를 고립시켜 검증
  /------------\
  • 단위 테스트(unit): 함수·컴포넌트 하나를 외부 의존성에서 고립시켜 검증. 가장 빠르고 많아야 합니다.
  • 통합 테스트(integration): 모듈들이 DB·외부 API와 함께 올바르게 작동하는지 검증.

AI 코딩에서 테스트를 코드보다 먼저 두는 이유. 코드를 먼저 만들고 테스트를 나중에 쓰면, 그 테스트는 "기능이 요구하는 것"이 아니라 "AI가 써 놓은 것"을 확인하는 데 그칩니다. 즉 잘못된 동작을 그대로 정당화합니다.

"당신이 명세(spec)를 소유하고, AI가 구현을 소유한다. 그래서 AI는 자기 버그를 스스로 검증할 수 없다." — 실사용자 정리

5.3 CI/CD — GitHub Actions 맛보기

  • CI(지속적 통합): 코드를 자주 통합하고, 통합마다 자동으로 빌드·테스트·검사를 돌려 문제를 조기에 잡습니다.
  • CD(지속적 전달/배포): 통과한 코드를 자동으로 배포 가능 상태로 만들거나 실제 배포합니다.

바이브코딩 학습자에게 CI/CD는 "내가 깜빡한 테스트를 컴퓨터가 매번 대신 돌려 주는 자동 안전망"입니다. GitHub Actions는 .github/workflows/의 YAML로 정의합니다.

# .github/workflows/ci.yml
name: CI
on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

permissions:
  contents: read          # 최소 권한 원칙

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<full-SHA>   # 뮤터블 태그 대신 전체 SHA 고정
      - uses: actions/setup-node@<full-SHA>
        with:
          node-version: '20'
      - run: npm ci
      - run: npm run lint
      - run: npm test

보안 수칙: 모든 액션을 전체 SHA로 고정(@v4·@latest 같은 뮤터블 태그 금지), 최소 권한(permissions 명시), 비밀 스캐닝·push protection 켜기.

5.4 SOLID / Clean Code 요약

SOLID는 객체지향을 넘어 복잡성 관리의 보편 원칙입니다 — "코드를 누가 썼느냐"가 아니라 "소프트웨어 복잡성의 물리학"을 다룹니다.

원칙한 줄 요약
SRP 단일 책임한 모듈은 한 가지 이유로만 바뀐다.
OCP 개방-폐쇄확장에 열려 있고 수정에 닫혀 있다.
LSP 리스코프 치환하위 타입이 상위 타입을 깨지 않고 대체한다.
ISP 인터페이스 분리안 쓰는 인터페이스에 의존하게 하지 마라.
DIP 의존성 역전구체가 아니라 추상에 의존하라.

Clean Code 핵심: 의도가 드러나는 이름(d 대신 daysSinceLastLogin), 작은 함수(한 가지만), 주석보다 코드로 설명, 중복 제거(DRY), 빠른 실패(fail fast).

AI는 작동하는 함수를 초 단위로 만들지만, 강결합·추상화 빈약한 코드도 그만큼 빨리 만듭니다. 설계 원칙을 아는 사람이 AI 산출물을 리뷰해 구조적 문제를 복리로 불어나기 전에 잡습니다. 자세한 내용은 소프트웨어 엔지니어링 가이드 참고.

✓ 체크포인트 최근 커밋 하나를 Conventional Commits 형식으로 다시 써 보고, 자기 앱의 위험도 높은 기능 하나에 단위 테스트 1개를 추가했으면 OK.

6. 도구가 대신 해주는 것 vs 내가 알아야 하는 것

🤖 도구가 대신 해주는 것

  • 보일러플레이트 코드 타이핑
  • 표·인증·라우팅 스캐폴딩
  • API 호출 코드 생성
  • "동작하는" 코드 생성
  • 빠른 반복·프로토타이핑
  • 의존성 추가 제안

🧠 내가 반드시 알아야 하는 것

  • 무엇을 만들지(아키텍처·데이터 모델) 설계
  • 그 스캐폴딩이 안전한 설정인지 검증
  • 비밀키가 코드에 박혔는지 확인
  • 그 코드가 옳고 안전한지 테스트·리뷰
  • N+1·과도한 리렌더 등 성능 함정 점검
  • 정식 패키지명·CVE 확인(공급망)

핵심. AI 생성 코드는 인간 작성 코드보다 결함·취약점이 더 자주 들어간다는 보고가 일관되게 나옵니다. "실행하기 전에 읽어라(Read before you run)." 검증의 책임은 사람에게 남습니다.

7. 실습 — 정적 → 동적 → API → 배포 한 줄기

이 한 줄기를 직접 통과하면 3계층·데이터·SE 실천이 머릿속에서 하나로 연결됩니다.

🖼️스크린샷1단계 결과: 정적 페이지(제목·문단·버튼)가 브라우저에 뜬 화면

1단계 — 정적(static)

HTML/CSS만으로 화면을 만듭니다. 서버 없이 파일을 브라우저로 엽니다. (이 김선생 가이드 사이트가 정적 사이트의 예입니다.)

✓ 체크포인트 제목·문단·버튼이 있는 정적 페이지가 브라우저에 뜨면 OK.

2단계 — 동적(dynamic)

JavaScript로 이벤트·상태를 붙입니다. 버튼 클릭 → 상태 변경 → DOM 갱신 루프를 만듭니다. 데이터를 localStorage에 저장해 새로고침해도 남게 합니다.

✓ 체크포인트 버튼을 누르면 화면이 바뀌고, 새로고침해도 값이 유지되면 OK.

3단계 — API

도구로 백엔드(예: Supabase)를 붙여 서버 DB에 저장합니다. ERD(2장)대로 표를 만들고, fetch로 데이터를 읽고 씁니다. 비밀키는 .env로, .gitignore에 추가합니다.

🖼️스크린샷3단계 결과: 다른 기기·브라우저에서도 같은 데이터가 보이는 화면
✓ 체크포인트 한 기기에서 저장한 데이터가 다른 기기·브라우저에서도 보이면 (= 진짜 서버 DB) OK.

4단계 — 배포(deploy)

GitHub에 올리고(Conventional Commits) 정적 호스팅 또는 도구 배포 기능으로 공개합니다. 가능하면 최소 CI(5.3)로 빌드·테스트를 자동화합니다.

✓ 체크포인트 공개 URL을 다른 사람에게 보냈을 때 정상 접속되고, 비밀키가 노출되지 않았으면 OK.

배포·CI/CD를 더 깊게: 소프트웨어 엔지니어링 가이드와 배포 개발자편을 잇습니다.
