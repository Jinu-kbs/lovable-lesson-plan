왜 "밑의 지식"이 필요한가

바이브코딩 도구는 자연어 한 줄로 화면과 버튼, 데이터베이스까지 만들어 줍니다. 그러나 도구가 만들어 준 결과물은 결국 HTML·CSS·JavaScript·HTTP라는, 30년 넘게 변하지 않은 웹의 토대 위에서 작동합니다.

핵심 메시지는 하나입니다. 바이브코딩은 "타이핑"을 대신해 줄 뿐, "생각"을 대신해 주지는 않습니다. 도구에게 좋은 지시를 내리고, 결과를 검증하고, 막혔을 때 원인을 짚으려면 이 토대가 머릿속에 있어야 합니다.

비유: 자동변속기 차를 몰 때 변속기 톱니바퀴를 직접 조작할 필요는 없습니다. 하지만 "엔진·브레이크·연료·타이어"가 무엇인지는 알아야 안전하게 운전하고, 차가 이상할 때 정비소에 정확히 설명할 수 있습니다. 이 교안은 바이브코딩의 "운전 상식"입니다.

1. 웹은 요청과 응답의 대화다

웹의 모든 것은 클라이언트(client)가 요청(request)을 보내고, 서버(server)가 응답(response)을 돌려주는 단순한 대화 구조로 환원됩니다.

[클라이언트/브라우저]  ──── 요청(Request) ────▶  [서버]
                       ◀──── 응답(Response) ────
  • 클라이언트(Client): 사용자가 직접 만지는 쪽. 보통 웹 브라우저(크롬·사파리·엣지)이며, 모바일 앱도 클라이언트입니다. "데이터를 보여 달라"고 요청하는 주체입니다.
  • 서버(Server): 인터넷 어딘가에 항상 켜져 있는 컴퓨터. 요청을 받아 처리하고 응답을 돌려줍니다.

클라이언트와 서버는 물리적으로 떨어진 두 컴퓨터입니다. 유튜브를 보든, 인스타에 사진을 올리든, 러버블로 만든 앱에서 버튼을 누르든 — 내부에서는 모두 이 요청-응답이 수십·수백 번 오갑니다. 바이브코딩 도구가 "백엔드를 연결했다"고 말할 때, 그것은 곧 "서버 쪽에서 요청을 처리할 코드와 저장소를 붙였다"는 뜻입니다.

✓ 체크포인트 "내 화면(클라이언트)이 서버에 무언가를 요청하고, 서버가 답(응답)을 준다"는 한 문장을 스스로 말로 설명할 수 있다.

2. 주소의 비밀 — URL과 DNS

사람은 youtube.com 같은 도메인 이름을 쓰지만, 컴퓨터는 142.250.x.x 같은 IP 주소로만 서로를 찾습니다. 이 둘을 연결해 주는 것이 DNS(Domain Name System) — 웹의 전화번호부입니다.

브라우저가 주소창의 도메인을 IP로 바꾸는 과정(이름 해석):

  1. 브라우저/OS가 로컬 DNS 캐시에 해당 도메인의 IP가 있는지 확인합니다 (이미 방문했으면 여기서 끝).
  2. 없으면 DNS 서버에 "이 도메인의 IP가 뭐냐"고 물어봅니다.
  3. DNS 서버가 IP를 알려 주면, 그제서야 브라우저가 그 IP의 웹 서버와 실제 통신을 시작합니다.

URL(Uniform Resource Locator) 은 "자원을 어디서 어떻게 가져올지"를 한 줄에 담은 주소입니다.

https://example.com:443/products/shoes?color=red#reviews
└─┬─┘   └────┬────┘ └┬┘ └────┬─────┘ └───┬────┘ └──┬──┘
프로토콜    도메인    포트    경로(path)   쿼리스트링  프래그먼트
(스킴)                               (?뒤 파라미터)  (#앵커)
  • 프로토콜(스킴): https:// — 어떤 규약으로 통신할지. s는 암호화(보안)를 뜻합니다.
  • 도메인: example.com — 어느 서버인지.
  • 포트: :443 — 그 서버의 어느 "문"으로 들어갈지 (HTTPS 기본 443, 생략 가능).
  • 경로(path): /products/shoes — 서버 안의 어느 자원인지.
  • 쿼리스트링: ?color=red — 서버에 넘기는 추가 조건/파라미터.
  • 프래그먼트: #reviews — 한 페이지 안의 특정 위치(앵커). 서버로 전송되지 않고 브라우저가 처리합니다.
✓ 체크포인트 내가 만든 사이트 주소가 https://my-app.lovable.app/dashboard?tab=stats처럼 보일 때, 각 조각(프로토콜·도메인·경로·쿼리)을 가리킬 수 있다.

3. 상태 코드로 읽는 신호 — 디버깅 첫걸음

서버는 요청에 대해 "결과가 어땠는지"를 숫자(상태 코드, status code)로 알려 줍니다.

범위의미대표 코드
2xx성공200 OK, 201 Created
3xx리다이렉트(다른 곳으로)301, 304 Not Modified
4xx클라이언트 잘못404 Not Found, 401 Unauthorized, 403 Forbidden
5xx서버 잘못500 Internal Server Error, 503

바이브코딩 중 "왜 안 되지?" 상황의 절반은 이 코드로 1차 진단됩니다. 외울 것은 단 두 가지입니다:

  • 4로 시작하면 내가(요청이) 잘못한 것 — 주소 오타, 로그인 안 됨, 권한 없음.
  • 5로 시작하면 서버 쪽 문제.

도구의 콘솔/네트워크 탭에서 이 숫자를 읽을 줄 아는 것만으로도 막연한 공포가 절반으로 줄어듭니다.

✓ 체크포인트 404와 500을 봤을 때, 각각 "내 쪽 문제"인지 "서버 쪽 문제"인지 구분할 수 있다.

4. 화면을 만드는 3형제 — HTML·CSS·JS

프론트엔드(눈에 보이는 쪽)는 세 가지 언어의 분업으로 만들어집니다.

언어역할집짓기 비유한 줄로
HTML구조(Structure)골조·벽·방 배치"무엇이 있는가"
CSS표현(Presentation)페인트·벽지·가구 배치"어떻게 보이는가"
JavaScript동작(Behavior)전기·수도·자동문"어떻게 움직이는가"

이 관심사의 분리(separation of concerns) 덕분에, 색을 바꾸려고 글의 내용을 건드리지 않아도 되고, 한 곳을 고쳐도 다른 곳이 안 망가집니다.

4.1 HTML — 의미를 가진 구조

HTML은 태그(tag) 로 콘텐츠에 의미를 붙입니다.

<article>
  <h1>제목입니다</h1>
  <p>본문 문단입니다. <a href="/link">링크</a>도 있습니다.</p>
  <button>클릭</button>
</article>

<div>만 쓰지 않고 <header>, <nav>, <button>처럼 의미가 있는 태그(시맨틱 HTML) 를 쓰면 검색엔진이 내용을 더 잘 이해하고, 스크린리더가 구조를 읽어 줄 수 있습니다.

4.2 CSS — 보이는 방식

CSS는 "어떤 요소를(선택자) 어떻게 꾸밀지(속성)" 규칙으로 표현합니다.

button {              /* 선택자: 모든 button을 */
  background: #7D3FEA; /* 속성: 보라색 배경 */
  color: white;
  padding: 12px 24px;
  border-radius: 8px;
}

4.3 JavaScript — 동작

JS는 사용자의 행동(클릭·입력)에 반응해 화면을 바꿉니다.

const button = document.querySelector('button');
button.addEventListener('click', () => {
  alert('버튼이 눌렸습니다!');
});

바이브코딩 연결: 도구에게 "버튼을 만들어"라고 했을 때 결과가 <div onclick>인지 <button>인지는 접근성에 큰 차이를 낳습니다. 의미를 알면 더 좋은 결과를 요구할 수 있습니다.

✓ 체크포인트 "구조는 HTML, 꾸미기는 CSS, 움직임은 JS"를 짝지어 말할 수 있다.

5. 내가 쓴 코드가 화면이 되는 과정

브라우저가 응답으로 받은 HTML·CSS·JS를 화면에 그리는 과정을 렌더링(rendering) 이라 합니다. 큰 흐름은 이렇습니다:

1. 주소 입력 → DNS가 IP를 찾음 (2장)
2. 브라우저가 서버에 요청 → 서버가 HTML 응답 (200 OK) (1·3장)
3. 브라우저가 HTML을 위에서부터 읽어 화면 구조(DOM)를 만듦
4. CSS로 색·여백·배치를 입힘
5. JS를 실행해 동작을 붙임 → 클릭하면 반응하는 살아 있는 화면

이 순서를 알면 "왜 이미지가 늦게 뜨는지", "왜 스크립트를 <body> 끝에 두는지" 같은 실전 감각이 생깁니다. 핵심: 내가 쓴 코드(HTML 파일)는 설계도이고, 브라우저가 그것을 읽어 그린 결과가 실제로 보이는 화면입니다.

✓ 체크포인트 "주소 입력 → 요청 → HTML 응답 → 브라우저가 그림"의 4단계 흐름을 순서대로 말할 수 있다.

6. 바이브코딩 도구가 대신 해주는 것 vs 내가 알아야 하는 것

도구가 대신 해주는 것 (타이핑)내가 알아야 하는 것 (생각)
HTML/CSS/JS 코드를 직접 작성"이 화면에 무엇이 있어야 하는가" 구조 판단
서버·DB 연결 자동 구성데이터가 어디에 저장·공유되는지 개념
에러 메시지 자동 수정 시도4xx(내 잘못)인지 5xx(서버 잘못)인지 읽기
반응형·접근성 기본 적용휴대폰 크기·키보드로 직접 점검
보기 좋은 디자인 제안"버튼은 <button>으로" 같은 더 나은 지시

도구는 "어떻게 만들지"를 대신하지만, "무엇을·왜 만들지"는 내 몫입니다. 이 한 줄이 이 교안 전체의 결론입니다.

7. 실습 — 아주 작은 정적 페이지 만들기

코드 한 줄도 안 무섭습니다. 따라만 하면 됩니다. 결과물은 "내 이름과 버튼이 있고, 버튼을 누르면 인사하는" 한 장짜리 웹페이지입니다.

7.1 파일 만들기

바탕화면에 my-first-page 폴더를 만들고, 그 안에 index.html이라는 파일을 만듭니다. (개발 인터페이스 초보자편의 터미널 실습을 했다면 mkdir/New-Item으로, 아니면 메모장/텍스트 편집기로 만들어도 됩니다.)

🖼️스크린샷바탕화면에 my-first-page 폴더와 그 안의 index.html 파일이 보이는 모습
✓ 체크포인트 index.html 파일이 폴더 안에 만들어졌다. 확장자가 .txt가 아니라 .html인지 확인한다.

7.2 HTML 뼈대 쓰기 (구조)

index.html을 편집기로 열고 아래를 그대로 입력합니다.

<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8">
  <title>나의 첫 페이지</title>
</head>
<body>
  <h1>안녕하세요, 김선생입니다</h1>
  <p>이것은 내가 만든 첫 번째 웹페이지입니다.</p>
  <button id="hello">인사하기</button>
</body>
</html>

저장한 뒤, 파일을 더블클릭하거나 브라우저로 끌어다 놓으면 화면이 뜹니다.

🖼️스크린샷브라우저에 제목·문단·버튼이 꾸밈 없이(검은 글씨) 표시된 모습
✓ 체크포인트 브라우저에 제목·문단·버튼이 보인다. 아직 색은 없어도 정상이다 — 지금은 구조(HTML)만 있는 단계다.

7.3 CSS로 꾸미기 (표현)

</head> 바로 위에 아래 <style> 블록을 추가합니다.

<style>
  body { font-family: sans-serif; max-width: 480px; margin: 40px auto; }
  h1 { color: #7D3FEA; }
  button {
    background: #7D3FEA; color: white;
    border: none; padding: 12px 24px;
    border-radius: 8px; cursor: pointer;
  }
</style>

저장 후 브라우저에서 새로고침(F5)하면 제목이 보라색이 되고 버튼이 예뻐집니다.

🖼️스크린샷제목이 보라색이고 버튼에 보라색 배경·둥근 모서리가 입혀진 모습
✓ 체크포인트 새로고침했더니 색과 모양이 바뀌었다. HTML은 그대로인데 CSS만 추가해 "보이는 방식"이 달라졌음을 확인한다.

7.4 JS로 움직이게 하기 (동작)

</body> 바로 위에 아래 <script> 블록을 추가합니다.

<script>
  const button = document.getElementById('hello');
  button.addEventListener('click', () => {
    alert('반갑습니다! 첫 페이지를 완성했어요.');
  });
</script>

저장 후 새로고침하고 버튼을 눌러 봅니다. 알림창이 뜨면 성공입니다.

🖼️스크린샷버튼을 누르자 "반갑습니다! 첫 페이지를 완성했어요." 알림창이 뜬 모습
✓ 체크포인트 버튼을 눌렀더니 알림창이 떴다. HTML(구조) + CSS(표현) + JS(동작) 3형제가 한 화면에서 함께 일하는 것을 직접 만들었다.

7.5 개발자도구로 들여다보기

브라우저에서 F12(또는 우클릭 → 검사)를 눌러 개발자도구를 엽니다.

  • Elements 탭: 내가 쓴 HTML이 브라우저 메모리 속 화면 구조(DOM)로 살아 있는 모습이 보입니다.
  • Network 탭: 새로고침하면 브라우저가 보낸 요청과 받은 응답(상태 코드 200)이 줄줄이 뜹니다 — 1·3장에서 배운 요청-응답이 실제로 보이는 순간입니다.
🖼️스크린샷개발자도구 Network 탭에 index.html 요청과 상태 코드 200이 표시된 모습
✓ 체크포인트 Network 탭에서 200을 직접 봤다. 이 사이트의 게시판이 서버 DB 없이 브라우저에만 저장(localStorage)된다는 점도 떠올려, "왜 진짜 서비스는 서버가 필요한가"를 생각해 본다.

🧠 이해했는지 확인해 보세요

아래 질문에 스스로 답한 뒤, 펼쳐서 정답을 확인하세요.

Q1. 404와 500 중 "서버 잘못"을 뜻하는 코드는?

정답: 500. 4로 시작하는 4xx는 클라이언트(내 요청) 잘못, 5로 시작하는 5xx는 서버 쪽 문제입니다. 404 Not Found는 주소 오타 등 요청 잘못입니다.

Q2. 화면을 만드는 3형제 중 "구조·뼈대"를 담당하는 언어는?

정답: HTML. HTML이 구조(뼈대), CSS가 꾸미기(스타일), JavaScript가 동작(상호작용)을 맡습니다.

Q3. 바이브코딩은 "무엇"을 대신해 줄 뿐, "무엇"은 대신해 주지 못하나?

정답: "타이핑"을 대신해 줄 뿐, "생각"은 대신해 주지 못합니다. 그래서 좋은 지시를 내리고 결과를 검증하려면 웹의 토대 지식이 필요합니다.
